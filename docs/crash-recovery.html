The very basics 가장 기본

An order book exchange that runs as a blockchain

블록체인으로 동작하는 호가창 거래소

People post buy and sell orders. A matching engine pairs them by price, then time. Instead of one company's database being the truth, every order and every fill is a transaction in a block, and several machines re-run each block to check they reach the same balances. That is all “Layer 1 exchange” means here.

사람들이 매수·매도 주문을 낸다. 매칭 엔진이 가격, 그다음 시간 순으로 짝을 짓는다. 한 회사의 DB가 진실이 되는 대신, 모든 주문과 체결이 블록 속 트랜잭션이 되고, 여러 기계가 각 블록을 다시 실행해 같은 잔고에 도달하는지 확인한다. 여기서 “레이어 1 거래소”란 그 뜻이다.

What survives when a node dies 노드가 죽으면 무엇이 남는가

The sequencer is not in the database. Its output is.시퀀서 자체는 DB에 없다. 시퀀서의 결과가 DB에 있다.

Every block and every row of state — accounts, orders, both book indexes, positions, funding, oracle — lands in RocksDB in one atomic batch. The in-memory books and accounts are a cache of that. After a crash the node rebuilds from RocksDB. What it can lose is whatever had not reached the disk yet (at most 8 blocks, MAX_PENDING), and the one dangerous case is a power cut after a block was already sent to others.

모든 블록과 상태 행(계정, 주문, 양쪽 호가 인덱스, 포지션, 펀딩, 오라클)은 하나의 원자적 배치로 RocksDB에 기록된다. 메모리 속 호가창과 계정은 그 캐시일 뿐이다. 장애 후 노드는 RocksDB에서 다시 만든다. 잃을 수 있는 것은 아직 디스크에 닿지 않은 것뿐이며(최대 8블록, MAX_PENDING), 위험한 경우는 하나 — 블록을 이미 다른 노드에 보낸 뒤 전원이 나가는 경우다.

Why a power cut is different from a kill정전이 프로세스 종료와 다른 이유

RocksDB writes go to its write-ahead log with sync = false. The bytes are in the operating system's page cache the moment write() returns. If only the process dies, the OS still flushes them, so nothing is lost. If the machine loses power first, the last few hundred milliseconds of writes can vanish.

RocksDB 쓰기는 sync = false로 WAL에 기록된다. write()가 반환되면 데이터는 OS 페이지 캐시에 있다. 프로세스만 죽으면 OS가 결국 디스크에 쓰므로 잃는 것이 없다. 기계 전원이 먼저 나가면 마지막 수백 ms의 쓰기가 사라질 수 있다.

That matters only for data somebody else has already seen. The sequencer announces a block to replicas and the gateway right after the write returns (on_durable in cb-node/src/sequencer.rs), not after a flush. Lose that block to a power cut and the restarted sequencer builds a different block at the same height; replicas holding the first one refuse it and halt.

문제는 이미 다른 누군가가 본 데이터일 때만 생긴다. 시퀀서는 쓰기가 반환된 직후(cb-node/src/sequencer.rs의 on_durable, 디스크 flush 전) 복제본과 게이트웨이에 블록을 알린다. 정전으로 그 블록을 잃으면 재시작한 시퀀서는 같은 높이에 다른 블록을 만들고, 원래 블록을 가진 복제본은 이를 거부하고 멈춘다.

What would close the gaps빈틈을 막는 방법

Sync each block before announcing it알리기 전에 블록마다 fsync

A synced write per block on the writer thread, before the announcement. Costs a few milliseconds a block, off the matching thread. Closes the fork.

작성 스레드에서 알림 전에 블록마다 동기 쓰기. 블록당 수 ms, 매칭 스레드 밖에서 발생. 포크를 막는다.

Serve RPC reads from sealed state onlyRPC 읽기는 봉인된 상태에서만

Today getAccount, positions and the order book read through the in-memory overlay, so a balance read just before a crash can revert — for the gateway's users too, since the gateway reads balances that way. Blocks and the block stream already come from the durable view. The existing --sync-writes flag removes the overlay (writes happen inline) but still does not fsync.

현재 getAccount, 포지션, 호가창 조회는 메모리 오버레이를 거치므로 장애 직전에 읽은 잔고가 되돌아갈 수 있다 — 게이트웨이도 그 방식으로 잔고를 읽으므로 게이트웨이 사용자도 해당된다. 블록과 블록 스트림은 이미 디스크 기준 뷰에서 온다. 기존 --sync-writes 플래그는 오버레이를 없애지만(쓰기를 즉시 수행) fsync는 하지 않는다.

Sync the BFT safety recordBFT 안전 기록 fsync

One small synced write before each vote. Removes the power-cut double vote, at a latency cost to measure against the sub-15 ms commit.

투표 전 작은 동기 쓰기 하나. 정전 시 이중 투표를 없애며, 15 ms 미만 커밋 목표에 대한 지연 비용은 측정이 필요하다.

Run BFT for anything real실제 운영은 BFT로

With four validators, one dying costs nothing: the other three keep committing, and the dead one refetches what it missed.

검증자 4개면 하나가 죽어도 손실이 없다. 나머지 셋이 계속 커밋하고, 죽은 노드는 놓친 것을 다시 받아온다.
