# Exchange and security audit

Reviewed commit: `9c2ab02ff3360ffbf9468763a430dcc81e22b6df`.
Started 2026-09-29; completed 2026-09-30 (Asia/Seoul).

## Remediation status

The implementation documented in the [changelog](../CHANGELOG.md)
fixes the five reproduced findings below. The remainder of this report records
what was observed at the audited commit, not the behavior after remediation.
The former witnesses are now enabled regression tests asserting safe behavior.
See [ADR 0009](adr/0009-audit-risk-and-block-identity.md) for the new rules and
fresh-chain requirement. Broader prototype limitations remain open.

## Assessment

The architecture makes sense as an exchange research prototype: deterministic
execution, a pure matcher, fixed-point accounting, transactional rollback,
signature verification at trust boundaries, and explicit separation of
application data from chain state are useful foundations. However, the current
implementation is unsafe for real funds and should be used only as a local
research prototype.

The most serious problems are financial solvency and the integrity of block
sync. Five focused executable witnesses reproduced unsafe behavior. Three
specific cases below were not listed in the existing security summary: an
insurance payout to a solvent hedged account, a closing maker order reopening
without margin, and block-hash malleability through certificate vote ordering.
The configured-risk and stale-price defects were already described in earlier
project reviews and remain present.

Severity below describes the consequences if this code backed real value.
The shipped environment uses test funds. “Reproduced” means an in-process test
against the real executor or sync implementation, not exploitation of a public
deployment. The audit itself did not change execution; the subsequent
remediation is described above and in ADR 0009.

## 1. Critical: insurance pays a solvent portfolio, and the account keeps the gain

**Reproduced.** `apply_collateral_delta` treats negative cash collateral as
bad debt and immediately calls `absorb_bad_debt`. The latter reduces both the
insurance balance and the account's debt. It does not check the account's
remaining positions or retain a claim against later gains.

Witness:

1. Fund an account with $2,200. Open long 1 BTC perpetual and short 1 BTC
   dated future, both at $50,000. The fixture gives both markets a $50,000 mark.
2. Move both marks to $47,000. One leg loses $3,000 and the other gains $3,000:
   total equity is still $2,200.
3. Close the losing leg at $47,000. Insurance pays the $800 by which the cash
   loss exceeds the account's collateral; its recorded debt returns to zero.
4. Close the winning leg at $47,000. The account receives $3,000 and keeps it.

Final state: the account has **$3,000 instead of $2,200**, the counterparty's
cash is unchanged, all positions are closed, and insurance has lost **$800**.
Every fill is at its market's mark. This does not need an out-of-band price or
a compromised oracle. Fees are zeroed in the fixture to isolate accounting;
fees do not repair the erroneous insurance eligibility decision.

This is distinct from the already documented colluding close at the edge of
the price band: a solvent hedge qualifies for insurance solely because the
losing leg closes first. Closing the profitable leg first avoids the cash
shortfall. That order dependence is an accounting defect.

**Locations:**
`rust/crates/cb-block/src/executor.rs:1417` and `:2387`.

**Fix direction:** track signed cash liabilities within cross margin and judge
bankruptcy against the entire account. Insurance should cover a verified
residual deficit after the bankruptcy/liquidation procedure, with a defined
policy for remaining positions and collateral. Do not extinguish liabilities
merely because an individual realization exceeds current cash. Add invariants
that insurance never subsidizes a solvent account and that equivalent hedge
unwinds cannot create trader profit at insurance's expense.

## 2. High: certificate malleability can strand a syncing node

**Reproduced using four real consensus engines and the real block-sync path.**

`Finality.cert.votes` is an aggregation of separately signed votes. Its
ordering is not signed, and certificate verification accepts different orders.
However, `BlockHeader::hash` hashes the entire serialized header, including the
certificate bytes in `parent_qc`.

The witness takes an honestly produced block, reverses only its certificate's
vote vector, and feeds it to a fresh observer. All original signatures remain
unchanged. The observer accepts the block and stores its altered hash. The
next honest block is then rejected with `SyncError::WrongParent`.

An attacker needs the ability to supply a block to a syncing node, not a
validator key. This is a concrete fork of block identity and sync failure;
the witness does not demonstrate conflicting transaction execution among the
four honest consensus engines. Validator catch-up also uses executed-block
sync, increasing the significance of this boundary.

**Locations:**
`rust/crates/cb-consensus/src/bft/types.rs:159` (certificate verification),
`rust/crates/cb-block/src/header.rs:43` (hash),
`rust/crates/cb-net/src/syncer.rs:170` and `:339` (proof acceptance / linkage).

**Fix direction:** define block identity using canonical committed content;
keep variable proof material outside the block ID. Alternatively bind the exact
canonical proof representation through consensus. Sorting votes alone does not
solve all certificate variability: different valid quorum subsets can also
produce different bytes. Test reordering, alternative quorum subsets and
additional valid votes, not only invalid signatures or insufficient quorums.

## 3. High: a closing maker order can later open an uncollateralized position

**Reproduced.** A plain order that `closes_only` regards as closing skips the
initial-margin gate. It remains a non-reduce-only order in the book. A later
reduce-only close also skips the margin gate and does not cancel or reserve
collateral for that earlier plain order. Maker execution does not recheck its
owner's margin.

Witness:

1. With $1,000 collateral, open a 1 BTC long at $50,000. Move the mark to $49,010.
2. Place a plain GTC sell for 1 BTC at $49,011. It is admitted as closing.
3. Close the long using a separate reduce-only sell at $49,010. Cash is now
   $10, the account is flat, and the old sell remains in the book.
4. Another account buys the old sell. It opens a new 1 BTC short for its owner.

The new position has **$11 equity against $980.20 initial margin**. The opening
fill succeeds despite being grossly undercollateralized. Fees are disabled in
this witness to isolate the bypass.

**Locations:**
`rust/crates/cb-block/src/executor.rs:1068`, `:1237`, and `:1570`;
`rust/crates/cb-engine/src/book.rs` revalidates explicit reduce-only makers but
does not perform a maker-margin check.

**Fix direction:** after any change to a position or collateral, preserve the
margin backing ordinary resting orders, or cancel/reduce those orders. An
order admitted with closing-only privileges must not silently turn into an
unfunded opening order. Revalidate maker solvency before increasing exposure.

## 4. High: configured risk limits are not enforced by execution

**Reproduced; previously reported in `docs/flow-review.md` finding 22.**

The executor uses `DEFAULT_TIERS` for initial margin and liquidation instead
of the market's `initial_margin_bps`, `maintenance_margin_bps` and
`max_leverage_x100`. `max_position_notional` is also not enforced on the
trading path. Tick and lot checks have been added since the old review and
are not part of this remaining finding.

The witness configures **1x leverage, 100% initial margin and a $1,000 position
cap**. The chain nevertheless accepts **$50,000 exposure with $1,000
collateral**, using the default 2% initial margin. The gateway and market
metadata can therefore describe materially different risk rules from the
ones protecting the chain.

**Locations:** `rust/crates/cb-block/src/executor.rs:1128` and `:2137`;
`rust/crates/cb-engine/src/margin.rs:94`.

**Fix direction:** use one consensus risk configuration for order admission,
resting-order exposure, liquidation and user-facing estimates. Enforce position
and leverage caps and define how market limits combine with tier requirements.
Exercise direct node submission as well as gateway validation.

## 5. High: arbitrarily stale marks still authorize trading

**Reproduced; already acknowledged in `SECURITY.md`.** The chain reads a
positive mark without checking its age against the executing block. The
witness opens a new 1 BTC position using a mark more than **1,000,000 blocks
old**. This bypasses gateway freshness checks by using the execution path
directly. The same stale marks feed equity and liquidation decisions.

**Location:** `rust/crates/cb-block/src/executor.rs:2688`.

**Fix direction:** enforce freshness in consensus using a specified source of
chain time or block age. Define safe behavior separately for increasing
exposure, cancelling orders, reducing exposure and liquidation. A blanket halt
that prevents users reducing risk needs careful consideration.

## Other blockers confirmed by source review

These are mostly documented design limitations, not newly discovered exploits.

- **Custody is centralized.** The gateway derives every trading key from its
  server secret and the public login address. A compromised gateway secret
  compromises all those trading accounts. Wallet login signatures do not make
  subsequent trades user-signed. See
  `rust/crates/cb-gateway/src/auth/eth.rs:550`. A noncustodial design needs
  user-signed actions or appropriately scoped, revocable delegation.
- **Real deposit/withdrawal custody is absent.** `Deposit` is authorized
  unlimited minting by the treasury; both withdrawal variants are unsupported
  (`executor.rs:340` and `:367`). `AdjustMargin` is also unsupported
  (`executor.rs:478`), so a complete user-funded margin lifecycle is missing.
- **Oracle trust is concentrated.** One configured authority can submit a
  market's price, without an independent corroboration rule or meaningful jump
  bound. Staleness protection alone will not protect against that authority's
  compromise. `executor.rs:495` contains the authority/update path.
- **Finality proofs are weaker than the commit rule.** The sync proof verifies
  a single QC, whereas the engine commits through a consecutive two-certificate
  rule. A certified proposal is not necessarily committed. This existing
  `SECURITY.md` issue is separate from certificate-byte malleability above.
  See `bft/types.rs:348` and `bft/engine.rs:1209`.
- **Consensus safety storage is not power-loss durable.** `persist_safety`
  uses a non-fsynced write; additionally `load_safety` logs and ignores an
  undecodable safety record. A safety-critical restart should fail closed on
  corruption and persist the voting floor durably before votes leave the node.
  See `rust/crates/cb-node/src/validator.rs:194`.
- **Insurance exhaustion has no complete loss-allocation mechanism.** The
  code can leave bad debt while crediting counterparties and put a market in
  reduce-only mode. That flag does not by itself restore solvency. Existing
  closing-order manipulation inside the 10% band also remains documented.
- **Public-network denial-of-service exposure remains.** Consensus messages
  are forwarded from handshaked peers without requiring validator membership;
  transaction batches and queues need byte/CPU budgets in addition to message
  counts. Published development validator, oracle and treasury seeds remain
  unsuitable for a public deployment. See `SECURITY.md` for the shipped-mode
  warnings and remaining RPC/P2P limits.

## Verification and scope

The four original executor witnesses in
`rust/crates/cb-block/tests/audit_20260929.rs` reproduced the stated behavior.
The certificate witness in `rust/crates/cb-node/tests/bft_execution.rs` did too;
its replacement regression is
`audit_20260929_reordered_certificate_preserves_block_identity`.

At the audited commit these were ignored witnesses of vulnerable behavior.
The remediation converts them to enabled regressions and adds boundary cases. Run from `rust/`:

```sh
ulimit -n 8192
cargo test --offline -p cb-block --test audit_20260929 -- --nocapture --test-threads=1
cargo test --offline -p cb-node --test bft_execution audit_20260929 -- --nocapture --test-threads=1
```

The initial audit attempt hit the local open-file limit while opening parallel
RocksDB fixtures. The witnesses reproduced with a raised limit and serial
execution; the audit's broader rerun was stopped before completion.

After remediation, validation completed on 2026-09-30:

- `make format-check`: passed (workspace and cb-web).
- `cargo clippy --offline --workspace --all-targets -- -D warnings`: passed.
- `ulimit -n 8192` followed by
  `cargo test --offline --workspace --no-fail-fast -- --test-threads=2`:
  **2,125 passed, 0 failed, 55 existing tests ignored**, across 182 test binaries
  and doctest groups. The full run used permission for local sockets and the
  CLI configuration directory after the sandbox refused those accesses.
- The ten executor audit regressions, maker-budget/FOK unit test, alternate-QC
  sync regression, randomized conservation and crash simulations all passed.
  The crash check now requires every unpaid cash liability to belong to an
  account with a live position while insurance remains funded; conservation
  checks were retained.

This is not a dependency-advisory audit, formal consensus proof, or complete
frontend and deployment review. Ignored tests and browser end-to-end tests
were not run. It does not certify the program free of other defects.

Recommended order: fix insurance eligibility and liability accounting; remove
certificate-dependent block identity and supply complete commit proofs; close
the resting-order margin bypass; enforce risk configuration and mark freshness.
Before real funds, complete custody/withdrawals, oracle fault handling,
durable consensus safety and deterministic loss allocation. Throughput work
should be measured again after those checks are part of the production path.
